# Decisions Log

Chronological log of design decisions and their rationale. Read entries by number — items elsewhere in the docs reference them as `[Decision N]`.

---

1. **Person snapshot redesign** — `dim_member` was split into three objects to separate identity from state:
   - `person_identity` — stable one-row-per-person surrogate key registry. On a core system conversion, only `source_person_serial` changes here; all snapshot FKs are untouched.
   - `person_snapshot_daily` — partitioned snapshot. One row per person per load date. Contains PII.
   - `person_snapshot_monthly` — monthly subset copied from daily on the first run of each month. Keyed to last calendar day of the month.
   - `core_conversion_xref.sql` — dormant script; only needed on a core system conversion.

   **Why no surrogate key inside the snapshot?** A BIGSERIAL in a partitioned snapshot is a throwaway row counter, not a stable identity. Stable identity lives in `person_identity`; snapshots FK into it via `person_key BIGINT`.

2. **`snapshot_date DATE` is cadence-agnostic** — Both snapshot tables are partitioned by `snapshot_date`. Changing from monthly to daily (or back) requires zero DDL changes — only the Dagster schedule changes. `month_id INT (YYYYMM)` exists only in `dim_date` as a GROUP BY convenience column; it is never used as a fact table key.

3. **`dim_goals`** — Stub. Schema created, no data loaded. Values to be confirmed and seeded in a later pass.

4. **Schema-per-environment** — `dev`, `test`, `prod` are schema namespaces in the same Postgres database. `WAREHOUSE_SCHEMA` env var drives the active schema; `WarehousePgResource.get_engine()` injects it as `search_path` at connection time. One DDL file (`warehouse_schema.sql`) creates any environment. Switch with `switch_schema.py` (GUI) or `Set-WarehouseSchema.ps1` directly.

5. **Percentage storage** — All percentages stored as true decimals (0.1251, not 12.51). Divide by 100 on load from any source that stores display-formatted values.

6. **ATM grain split** — `fct_atm_by_machine_summary` for per-machine transaction counts. ATM network totals (member uses, foreign uses, YTD net income) in `fct_financial_ratios_summary`.

7. **`fct_members_added` / `fct_members_lost` idempotency** — `UNIQUE (source_system, source_person_serial, month_id)` on both tables enables `ON CONFLICT DO NOTHING` upsert semantics. Re-running a monthly partition silently no-ops on existing rows. Do not use delete-by-month or append-only patterns. (Originally a single combined `fct_members_added_lost` table — see Decision 25 for the split.)

8. **`home_branch_key` stores raw `CU_HOME_BRANCH`** — The per-person `home_branch_key` on snapshots stores `CORE.CU_HOME_BRANCH` directly. ZIP-territory assignment is an analytic interpretation applied only in the aggregate asset. This means `home_branch_key` on the snapshot and the branch counted in `fct_home_branch_members_summary` can differ for members whose ZIP territory doesn't match their `CU_HOME_BRANCH`.

9. **Person snapshot split — biographic vs. Keystone-specific** — `person_snapshot_daily/monthly` hold only stable biographic attributes (name, birth_date, gender, middle_name). System-specific data that changes at different rates was split out:
   - `person_contact` — contact info, independent of snapshot pipeline, loaded directly from DB2
   - `ks_products_snapshot` — product membership; long format (one row per person × product type)
   - `ks_relationships_snapshot` — account standing (status, eligibility, type)
   - `ks_credit_score_snapshot` — credit score + as-of date
   - `ks_member_branch_snapshot` — opening branch + home branch keys

   **Why split?** Credit score changes should not trigger a "person changed" flag. Different modules, different change rates, different BI use cases.

10. **Multi-source naming convention** — Three tiers:
    - **Canonical (no prefix):** `person_identity`, `person_source_identifier`, `person_contact` — span source systems
    - **Source-prefixed (`ks_`, `hs_`):** Mirrored or snapshot data from that system. Grain suffix required: `_snapshot` for partitioned history, `_events` for append-only, no suffix for current-state
    - **Analytics layer (`dim_*`, `fct_*`, `v_*`):** Never get a source prefix even if KS-sourced
    - `person_source_identifier` is the resolution table for all `person_key` lookups from source IDs

11. **`ks_relationships_snapshot` columns — `account_eligibility` + `account_type`** — The original `affiliation` column mapped to a CORE field that doesn't exist. Replaced with `CORE.ACCOUNT_ELIGIBILITY.DESCRIPTION` and `CORE.ACCOUNT_TYPE.DESCRIPTION`. `status` (Platinum/Silver from `CORE.ACCOUNT_RELATIONSHIP.DESCRIPTION`) is retained.

12. **`dim_employee.full_name` = username** — `CORE.USER` exposes only `USERNAME`, not first/last name. `full_name` is populated with the username value for v1. Update if name fields become available in a future CORE release.

13. **Teller assets source: JasperServer API** — Both `fct_teller_activity_table` and `fct_teller_out_of_balance_table` pull from JasperServer reports (`TellerDrawerOver-UnderMonthly` and `Transactions_By_Role_Type`). Parameter names are `StartDate`/`EndDate` (no underscores). Historical data was backfilled from exported CSVs.

14. **ELT architecture — `staging.ks_*` mirrors before PostgreSQL transforms** — All DB2 source tables are mirrored into staging on two tracks: daily `staging.ks_*` (nightly from LIVE) and monthly `staging.ks_*_monthly` (per-partition from the frozen snapshot DB, see Decision 36). Downstream assets read from staging and transform in PostgreSQL. This makes data backfillable, enables inspecting intermediate state in pgAdmin, and reduces DB2 load (each table queried once per cadence). These mirrors are **not raw verbatim copies** — they involve joins, filtering, and column selection. `staging.ks_transaction` and `staging.ks_monetary` use incremental loading on the daily track (append since MAX(posting_date), trim >90 days) — a full 90-day CORE.TRANSACTION reload was taking 15+ minutes.

15. **`staging.person_snapshot_stage` — person snapshot intermediary** — `ks_person_snapshot_stage_table` runs the DB2 complex person query once per job run (TRUNCATE + reload). Downstream snapshot assets read from it rather than re-querying DB2 independently. This ensures all six downstream assets see identical data within a run.

16. **`assert_staging_fresh` guard** — Every downstream snapshot asset calls `assert_staging_fresh(engine, "staging.ks_<table>", partition_date)` before writing. Raises `RuntimeError` if the upstream staging table was not loaded on the partition date. Dagster's dep graph shows the connection but does not enforce data currency — this guard is the hard check.

17. **`ks_products_snapshot` long format** — One row per person × product type (not wide format). `product_count SMALLINT` records how many accounts of that type the person holds. Enables direct product-presence queries and set-difference change detection without parsing text in SQL.

18. **Monthly snapshot uses MAX-in-month (dev), EOM-strict commented out** — `ks_person_snapshot_monthly_table` uses `MAX(snapshot_date)` within the calendar month so the asset can run before month-end. The monthly row is still keyed to `last_day_of_month(partition_key)`. EOM-strict version is preserved as commented-out code — uncomment when going to prod.

19. **`person_contact` as partitioned snapshot** — Redesigned from current-state upsert to partitioned snapshot (DELETE-before-INSERT per partition). `contact_label` dropped (redundant). `valid_from TIMESTAMPTZ` → `last_verified_date DATE`. Loaded independently from DB2 — not part of the person snapshot pipeline.

20. **`ks_products_snapshot.product_count`** — A member can hold multiple accounts of the same product type (e.g., two Additional Shares). `product_count SMALLINT DEFAULT 1` records the count per product type per person per date. PK `(snapshot_date, person_key, product_name)` is unchanged — one row per type, count in the column.

21. **Schema environment switching** — `WAREHOUSE_SCHEMA` env var + PostgreSQL `search_path` means one DDL file creates any environment. `audit_load()` in `loading.py` checks the `.schema_intent` file (written by `switch_schema.py`) against the running env var before every loader write — hard runtime gate independent of Dagster's dependency graph.

22. **`fct_nps_summary` split from `fct_financial_ratios_summary`** — NPS is a member satisfaction metric, not a financial ratio. Moved to its own table. `fct_financial_ratios_summary.nps_score` column removed.

23. **`fct_digital_channels_summary` demoted to stub** — Source CSVs for bill pay transactions, mobile/online transactions, and home banking activity counts do not exist. Table retained in schema as a stub; no load asset.

24. **Jobs consolidated to daily / monthly** — `ks_daily_job` (staging mirrors + dims + daily snapshots, 11pm nightly) and `ks_monthly_job` (monthly snapshots + JasperServer teller reports, 1am on 1st). Dagster resolves execution order from asset deps within each job. The daily schedule passes today's date as partition key; non-partitioned assets ignore it.

25. **`fct_members_added_lost` split into two tables** — Single combined event table proved awkward in practice: members added and lost have different per-month load cadences, different source queries, and different downstream consumers. Now `fct_members_added` (one row per person × month they joined) and `fct_members_lost` (one row per person × month they closed) are separate fact tables, each loaded by its own Dagster monthly-partitioned asset. Uniqueness is `(source_system, source_person_serial, month_id)` on both — re-runs idempotent via `ON CONFLICT DO NOTHING`.

26. **`fct_loans_by_branch_summary` derived from `staging.ks_loan`** — Originally CSV-sourced because `LOAN_REQUEST.BRANCH_SERIAL` was ~80% NULL. Discovered that `CORE.LOAN.BRANCH_SERIAL` (the *disbursing* branch on the funded loan, distinct from the requesting branch on the application) is fully populated. The asset now truncates and reloads from staging with breakdown columns `loan_count`, `payday_loan_count`, `non_payday_loan_count`. CSV backfill (`fct_loans_by_branch_summary_backfill`) is superseded but kept for historical 2020–2024 data only.

27. **OP Branch IS Overland Park Branch** — Same physical branch, two names. CORE stores `BRANCH.DESCRIPTION = "Overland Park Branch"`; the warehouse renamed `dim_branch.branch_name` to `"OP Branch"` to match staff terminology. Anywhere a branch name flows from CORE into a warehouse lookup, normalize through `CORE_TO_WAREHOUSE_BRANCH_NAME` in `warehouse_loaders/branch.py`. Without this, the home-branch fallback path (`assign_branch_with_fallback` returns `"Overland Park Branch"` when ZIP doesn't match an OP territory) silently dropped ~40-50 members per month at the `branch_totals.get("OP Branch", 0)` lookup. Fail-loud guard added to `ks_fct_home_branch_members_summary_table`: raises if any name in `branch_totals` is not in `dim_branch`.

28. **`Unassigned` preserved in fact table, folded into Main in view** — Members with no ZIP territory match and no `CORE.CU_HOME_BRANCH` assignment are written to `fct_home_branch_members_summary` under the `Unassigned` sentinel `branch_key` (preserving traceability — a count of ~15 members showed up as Unassigned in production and was previously dropped silently). Presentation view `v_home_branch_members_monthly` folds those counts into Main Branch via `CASE WHEN branch_name = 'Unassigned' THEN 'Main Branch'`. Rule: raw breakdown in facts, business roll-up in views.

29. **Monthly partition routing uses `context.partition_key`, not `today.day == 1`** — Original `resolve_db_for_scheduled_run` in `ks_db_connections.py` looked at `date.today().day == 1` to decide which DB2 snapshot DB to connect to (MONTH_END_1/2/QUARTER_END). This broke whenever a monthly asset was re-run on any day other than the 1st (manual backfill, gap-fill, etc.) — fell through to `LIVE`, which returns mid-month state and silently produces wrong "month-end" numbers. Fix: monthly job type now always derives the snapshot month from `context.partition_key`, looks up the correct frozen snapshot DB in `MONTH_SNAPSHOT_MAP`, and uses it regardless of run day or schedule/manual origin. `KEYSTONE_DB_OVERRIDE` is ignored for monthly partitions (with a warning) — partition key is the source of truth.

30. **BI presentation views (`v_*`)** — Added in 2026-06: `v_members_monthly` (pass-through of `fct_members_summary`), `v_home_branch_members_monthly` (Unassigned → Main fold), `v_members_lost` (slim projection of `fct_members_lost`), `v_loans_by_branch_lsi_in_main` (LSI rolled into Main). Defined in `warehouse_schema.sql` so they regenerate with every `warehouse_tables` materialization. Gold-layer rule: views strip metadata columns (`loaded_at`, internal FKs other than table PKs/SKs), join in branch names, and reshape facts for the BI tool. The base fact tables stay raw.

31. **`fct_members_branch_summary` dropped** — Briefly existed as an opening-branch member roll-up; redundant with `fct_home_branch_members_summary` for all dashboard purposes (opening-branch and home-branch metrics live elsewhere). Removed from `warehouse_schema.sql` and references purged from `repair_ops.py`, `schedules.py`, and `fct_members.py`. The physical table may still exist in `prod` until a `DROP SCHEMA CASCADE` rebuild — it's safe to drop manually with `DROP TABLE IF EXISTS prod.fct_members_branch_summary`.

32. **`fct_loans_by_branch_summary` has 3 count columns, not 1** — Schema extended to `loan_count` (total) + `payday_loan_count` (`loan_type = 'Payday Alternative Loan'`) + `non_payday_loan_count` (all others). Backfill CSV provided only the total; new staging-derived asset computes the split. Used by the loans-by-branch dashboard panel.

33. **`ks_person_snapshot_monthly_table` + `ks_person_monthly_snapshot_stage_table` converted from unpartitioned (`today.day != 1` guard) to `MonthlyPartitionsDefinition`** — Both assets previously self-determined the snapshot date from `date.today()` and silently skipped on any day other than the 1st. Any manual re-run on a non-1st day was a no-op — and any path that bypassed the guard (e.g. `ks_monthly_repair_table` invoking the same DB2 query independently) would happily load whatever the snapshot DB had under a snapshot_date derived from `today`, producing rows like the bad 2026-06-30 `person_snapshot_monthly` row that contained mid-June LIVE data. Now both assets derive snapshot_date from `context.partition_key`, the schedule's `partition_key` flows through, and re-runs are idempotent via DELETE+INSERT. See Decision 29 for the parallel fix in `ks_db_connections.resolve_db_for_scheduled_run`.

34. **`assert_snapshot_db_matches_partition()` guard** — New helper in `loading.py` that queries `CORE.ENV.POSTING_DATE` on the connected DB2 snapshot DB and raises if it doesn't equal the partition's EOM. Called from every monthly asset that connects via `keystone_database.get_connection(context=context, job_type="monthly")` plus the `ks_monthly_repair_table` recovery path. Catches two failure modes: (1) materialising a future partition where the routed snapshot DB hasn't refreshed yet (the bug that produced the bad 2026-06-30 rows), and (2) re-loading an old partition after the snapshot DB has rolled forward to a newer quarter.

35. **`ks_fct_loans_by_branch_summary_table` skips incomplete months** — Asset is non-partitioned and truncate-reloads from 2020-01-01 forward by grouping `staging.ks_loan.open_date` into EOM buckets. Without a guard, a mid-month run would emit a row for the current month containing only the loans opened so far — silently wrong data tagged with a future EOM. Now the WHERE clause filters `(date_trunc('month', open_date) + INTERVAL '1 month - 1 day')::date <= (SELECT posting_date FROM staging.ks_env)` so only months whose EOM has been reached emit a row.

36. **Monthly job gets its own `staging.ks_*_monthly` staging layer** — The daily `staging.ks_*` mirrors are refreshed nightly from LIVE. When monthly facts (`fct_members_summary`, `fct_loan_applications/requests/loans`) read from those daily mirrors, they pick up post-EOM members/loans and produce counts that drift from the frozen snapshot DB. 14 parallel monthly mirror tables (`staging.ks_share_monthly`, `staging.ks_person_monthly`, etc.) are loaded from the partition's frozen snapshot DB (MONTH_END_1/2 or QUARTER_END) by `MonthlyPartitionsDefinition` assets in `staging_tables_ks_monthly.py`. Every monthly fact asset now reads from the `_monthly` tables. After this rewrite, May 2026 `fct_members_summary` matches the manually-QA'd CSV exactly on total/KS/MO/active/18-50/added/lost. The home-branch numbers come from `fct_home_branch_members_summary` which already queried CORE directly via `keystone_database.get_connection(job_type="monthly")`.

37. **`ks_transaction_monthly` / `ks_monetary_monthly` are loaded by COPYING from daily staging, not pulling from DB2** — Both CORE tables are huge (~3.5M / ~530K rows for May 2026) and a fresh DB2 pull each month takes ~20 min. Instead, these two monthly assets `INSERT INTO ... SELECT FROM staging.ks_transaction WHERE posting_date BETWEEN window_start AND snapshot_date` against the daily 90-day rolling staging. The daily staging always covers the most recent ~90 days, which is more than enough for any partition's 30-day window when run within a few months of the partition. The asset fails loudly with a clear error if the daily window doesn't cover the required range (`MIN(posting_date) > window_start`). All other monthly staging tables pull fresh from DB2 against the snapshot DB.

38. **`hb_mo_members` includes Unassigned** — The `_compute_fct_members_summary` `hb` CTE previously excluded `'Unassigned'` from the `hb_mo` filter, causing the column to be ~15 lower than the verification CSV. The `v_home_branch_members_monthly` view already folds Unassigned into Main Branch (Decision 28) — `hb_mo` in `fct_members_summary` must match that fold or the BI numbers diverge from the fact table's CU-total summary. Now `hb_mo = SUM(total_members) FILTER (WHERE branch_name NOT IN ('CU Total', 'OP Branch', 'LSI Branch - Online Applications'))` — Unassigned is no longer excluded.

39. **`manual_entries_table` reads snapshot_date from the CSV's `__meta__` row, not from a partition** — Previously this asset was `MonthlyPartitionsDefinition` and derived the date from `last_day_of_month(partition_key)`. The month-end person fills out the CSV with values for one specific month and wants the date inside the file (one cell to edit) rather than juggling Dagster partition selectors. The asset is now unpartitioned; it reads the `__meta__,snapshot_date,YYYY-MM-DD,,` row at the top of `manual_entries.csv` and writes that date on every row it loads. Fails loudly if the meta row is missing or the value isn't a valid ISO date.

40. **`nps_score` routes to `fct_nps_summary` in manual_entries.csv** — Per Decision 22, NPS was split out of `fct_financial_ratios_summary` into its own table. The `manual_entries_table` asset originally still wrote `nps_score` into the financial ratios table (where the column no longer exists) — would have crashed on first month-end run. Now: the asset has a dedicated `INSERT INTO fct_nps_summary` block triggered when the CSV contains a `fct_nps_summary,nps_score,...` row, and the seed CSV's NPS row was re-routed to the correct table.

41. **`manual_entries_table` upserts use `COALESCE` to preserve existing values on blank cells** — Every `ON CONFLICT DO UPDATE` column wraps its assignment in `COALESCE(EXCLUDED.col, table.col)` so that NULLs from blank CSV cells don't overwrite previously-loaded values. Combined with the row-level "skip if value is blank" filter, this gives the manual entries CSV true cell-level targeting: editing one cell changes only that cell on that row, nothing else. Re-running the asset with everything blank is a no-op; re-running with one cell filled in updates one column. Without this guard, a partially-filled CSV would silently wipe out unrelated columns to NULL on conflict.

42. **`manual_entries.csv` gained a `row_key` column to support multi-row tables** — Originally the CSV's column-oriented format only worked for tables with `snapshot_date` as the sole PK. Composite-PK tables (`fct_branch_profitability_summary` keyed by `(snapshot_date, branch_key)`, `fct_atm_by_machine_summary` keyed by `(snapshot_date, atm_name)`) didn't fit because the asset couldn't tell which row of those tables a value belonged to. New 6th column `row_key` carries that identifier — blank for single-row tables (existing behavior preserved), branch_name for profitability, atm_name for ATM. The asset routes rows with non-empty `row_key` through table-specific handlers that resolve the second PK component (branch_name → branch_key for profitability; atm_name used directly for ATM) and upsert with the same COALESCE-on-conflict pattern as single-row tables.

43. **CSV-drop assets for `fct_branch_profitability_summary` and `fct_atm_by_machine_summary` retired** — These two tables are now populated via `manual_entries.csv` (Decision 42) since accounting hand-enters the values anyway and the drop-folder approach was an unused path. `fct_branch_profitability_summary_table` and `fct_atm_by_machine_summary_table` removed from `csv_loads.py`, their entries removed from the `_CSV_DROP_ASSET_MAP` in `sensors.py`, and `_CSV_BRANCH_TO_ABBREVIATION` constant removed (it had no other consumers). The `data/csv_drop/<table>/` folders are no longer monitored but left in place harmlessly. Remaining drop-folder assets: `fct_digital_enrollments_table` and `fct_survey_responses_table`.

44. **`home_banking_users` moved from CSV drop to `manual_entries.csv`** — The online banking platform dashboard only exposes a single monthly enrolled-users total, not a row-level export. Parsing a CSV that doesn't really exist (we were dumping the platform's user list just to `len()` it) was more work than typing the number into `manual_entries.csv`. The `online_banking` subfolder under `data/csv_drop/fct_digital_enrollments/` was removed, the `home_banking` service row was removed from `fct_digital_enrollments` (the table now carries only `bill_pay` and `rdc`), and the `fct_digital_channels_summary.home_banking_users` column is now owned entirely by `manual_entries_table`. The DELETE in `fct_digital_enrollments_table` was narrowed to `service IN ('bill_pay', 'rdc')` so it doesn't touch any historical `home_banking` rows. Remaining drop-folder assets: `fct_digital_enrollments_table` (bill_pay + rdc) and `fct_survey_responses_table`.

45. **HubSpot live-import producer moved from a manual notebook to the `hubspot_live_import_csv` asset** — The monthly HubSpot contact refresh was a hand-run notebook (`combine_keystone_hubspot_info.ipynb`): export all HubSpot contacts, run a DataGrip query to a `keystone_products_for_hubspot_pull` CSV, join/clean/transform into `hubspot_live_import.csv`, re-import. It's now the `hubspot_live_import_csv` asset (new `hubspot_exports` group). Notable points: (a) the generating Keystone query was never saved — the three checked-in "person service" variants all lacked `ALL_PAST_EMAILS`/`CURRENT_EMAIL`/`BIRTH_DATE`/`MIDDLE_NAME`/`MEMBER` — so it's now committed as `queries/keystone_products_for_hubspot.sql`, with a new `AllPastEmails` CTE (`LISTAGG` over all `PE`/`BE` emails, no bad/expiration filter) and a `MEMBER` YES/NO flag replacing the old `General Share` WHERE filter; (b) the product→category mapping the notebook read from a missing `Product To Product Category.csv` is now an editable checked-in reference (`reference/product_to_category.csv` + `load_product_category_map()`); (c) the transform (email-list explode → inner join on email+name → dedupe on person → Keystone-phone-preferred → drop birthdate-mismatch duplicate-email rows → product categories) is replicated exactly and covered by a golden test that reproduces the March `hubspot_live_import.csv` to the row (9,043) from the saved inputs. **This asset intentionally bypasses the warehouse and `load_audit`** — it reads a dropped HubSpot CRM export from `data/csv_drop/hubspot_live_import/` plus a live Keystone pull and writes a dated `hubspot_live_import_<YYYY-MM-DD>.csv` (+ `error_check_duplicates_<date>.csv`) to `data/csv_output/hubspot_live_import/`; observability is via `MaterializeResult` metadata. Output CSVs and the `hubspot_contact_update/` working CSVs are gitignored (member PII). The HubSpot async-export API (seen in `hubspot_export_api.ipynb`) is a possible future replacement for the manual CRM-export drop — out of scope for now.

46. **`fct_loan_portfolio_summary` had two duplicate YTD-growth-pct columns — one dropped, the survivors renamed for naming consistency** — `loan_ytd_difference_pct` (sourced from `CFO_Dashboard.csv`'s "Loan YTD Difference") and `loan_growth_ytd_pct` (sourced from `MarketingDBData.csv`'s "Loans" column) were the same metric loaded from two different spreadsheets (confirmed in `schema_design/04_source_decisions.csv`). The CFO_Dashboard-sourced column had complete data (77/77 rows) vs. the MarketingDBData-sourced column (76/77 rows), so the MarketingDBData-sourced `loan_growth_ytd_pct` was dropped and `loan_ytd_difference_pct` renamed to `loan_growth_ytd_pct` in its place — keeping the more complete data under the clearer name. `share_ytd_difference_pct` was also renamed to `share_growth_ytd_pct` for naming consistency with `cc_growth_ytd_pct`/`loan_growth_ytd_pct` (no data change — single source, no duplicate). The dependent view `v_cc_loans_growth_ytd_monthly` was repointed via `CREATE OR REPLACE VIEW` (it already referenced `loan_growth_ytd_pct`, which now resolves to the renamed column). `fct_loan_portfolio_summary_backfill` no longer reads `MarketingDBData.csv`'s "Loans" column (`CreditCards` → `cc_growth_ytd_pct` is still consumed). `manual_entries.csv` rows updated to the new column names.

47. **`home_banking_users` moved from `fct_digital_channels_summary` to `fct_digital_enrollments`** — Reverses the destination half of Decision 44. The monthly hand-entered home banking total is an *enrollment count*, the same metric `fct_digital_enrollments` already tracks per service (`bill_pay`, `rdc`) with `home_banking` history back to Jan 2020 from the original backfill — routing it into the channels-summary table split one series across two tables for no reason. The `home_banking_users` column was dropped from `fct_digital_channels_summary` (its one value, 2026-05-31 = 13095, migrated into `fct_digital_enrollments` first); the table now carries only the two transaction-count columns. `manual_entries.csv` routes the value via the multi-row pattern (`fct_digital_enrollments,enrolled_count,home_banking,...` — `row_key` = service name, validated against the known service set, fail-loud on anything else). The manual-entry source itself (Decision 44's other half — platform dashboard total instead of a CSV drop) is unchanged. With only the two transaction-count columns left, the table was renamed `fct_digital_channels_summary` → `fct_digital_channels_transactions` to match its contents (deliberate exception to the `_summary` aggregate suffix convention — "transactions" is the clearer description). Separately, the historical `fct_digital_enrollments` series contained mis-anchored values from the original positional backfill — corrected via a month-labeled backfill CSV (all three services, Jan 2020–Apr 2026, verified cell-for-cell) and a rewritten `fct_digital_enrollments_backfill` parser that reads explicit month labels instead of generating dates positionally.
